# Лабораторная работа №7 Шаблонизация

## Цель работы
Освоить принципы шаблонизации в PHP, как с использованием нативных PHP-шаблонов, так и с применением готового шаблонизатора. Улучшить структуру проекта, разделив логику обработки данных и представление.

## Условие
Продолжите разработку проекта из лабораторной работы №6, разделив его на слои: логику и представление. Работа выполняется в два этапа - сначала вы реализуете собственный механизм шаблонизации, затем подключаете Twig и реализуете ту же функциональность через него.

### Шаг 1. Рефакторинг. Нативные PHP-шаблоны
Перепишите существующий проект, разделив код на два уровня:

- Логика - PHP-файлы, которые обрабатывают запросы, читают/записывают данные и подготавливают переменные.
- Представление - отдельные .php-файлы-шаблоны, которые только отображают данные.

Один из примеров структуры проекта может выглядеть так:

```
project/
├── templates/
│   ├── layout.php       # Общий макет (header, footer)
│   ├── form.php         # Шаблон формы добавления записи
│   └── list.php         # Шаблон таблицы со списком записей
├── src/
│   ├── functions.php    # Функции для работы с данными
│   └── handler.php      # Обработчики запросов (например, для добавления новой записи)
├── index.php            # Точка входа, логика маршрутизации
└── data.json            # Файл с данными

```

В проекте должно быть показано использование как нативных PHP-шаблонов, так и готового шаблонизатора. Оба варианта должны присутствовать в проекте, чтобы можно было сравнить их между собой.

# Контрольные вопросы
1. В чём отличие нативных PHP-шаблонов от шаблонизатора Twig? Какие преимущества и недостатки у каждого подхода?

**Нативные PHP-шаблоны** — это обычные `.php` файлы, где HTML смешивается с PHP-кодом.

- не нужно устанавливать дополнительные библиотеки;
- быстрее начать;
- полный доступ к PHP.

Минусы:

- легко смешать логику и HTML;
- код становится грязным;
- сложнее поддерживать большой проект.

Twig — отдельный шаблонизатор с более чистым синтаксисом.

Плюсы:

- шаблоны выглядят аккуратнее;
- легче отделять HTML от PHP-логики;
- есть наследование шаблонов;
- безопаснее вывод данных через экранирование.

Минусы:

- нужно устанавливать через Composer;
- нужно изучить синтаксис Twig;
- чуть сложнее настройка проекта.

2. Зачем разделять логику и представление в проекте? Какие проблемы могут возникнуть, если смешивать их в одном файле?

- **Логика** — это обработка данных, работа с БД, проверки.

Представление — это HTML и вывод данных пользователю.

- Разделять нужно, чтобы:

    - код был понятнее;
    - легче было искать ошибки;
    - проще менять дизайн без изменения логики;
    - проект было легче расширять.

- Если всё смешивать в одном файле:

    - файл становится большим и запутанным;
    - сложно поддерживать код;
    - можно случайно сломать логику при изменении HTML;
    - труднее работать в команде.

3. Что такое наследование шаблонов в Twig? Как работают {% extends %} и {% block %}?

Наследование шаблонов позволяет создать общий шаблон, например `layout.twig`, а другие страницы будут его использовать.

`{% extends "layout.twig" %}` — говорит, что текущий шаблон наследует основной шаблон.

`{% block content %}` — место, которое можно переопределить в дочернем шаблоне.

**Пример:**

```php
{% extends "layout.twig" %}

{% block content %}
    <h1>Главная страница</h1>
{% endblock %}
```

То есть общий каркас сайта хранится в одном файле, а разные страницы меняют только нужные блоки.
